## 1. Зачем

Я плачу за три подписки — Claude Max, Codex Pro, OpenCode Go — и ни разу не
знаю, сколько у меня осталось, пока не упрусь. Упираюсь обычно посреди работы.

Всё это уже решено в Орке (`~/orca/app/core/`, порт с `stablyai/orca`), но там

меняем подачу.

## 2. Что делаем

**Этап 1 (эта спека).** Три кольца в капсуле меню-бара справа от цены — по
кольцу на провайдера, заполнение по проценту израсходованного лимита. Разбор
по окнам — внутри попапа на вкладке «Расходы». Сводного числа нет: окна
разнородные, честно сложить их пока нечем.

**Этап 2 (отдельной спекой).** Прогноз по темпу расхода: «при текущем темпе
Codex кончится завтра к 18:00, раньше сброса». Поэтому снапшоты пишем в базу
с первого дня — иначе на втором этапе стартуем с пустой историей.

Не делаем: уведомлений при приближении к потолку, истории лимитов графиком,
поддержки других харнесов.

## 3. Источники данных

Все три проверены живьём 2026-07-31.

### 3.1 Codex — локальный RPC

Спавним `codex -s read-only -a untrusted app-server`, говорим по JSON-RPC
через stdin/stdout: `initialize` → нотификация `initialized` →
`account/rateLimits/read`. Ответ:

```json
{"rateLimits": {"primary": {"usedPercent": 78, "resetsAt": 1785905362,
                            "windowDurationMins": 10080},
                "secondary": null}}
```

Локально, без сети, около секунды на вызов. Фолбэк, если бинаря нет или RPC
отвалился — последний снапшот `rate_limits` из свежих `~/.codex/sessions/**/rollout-*.jsonl`
(парсер уже есть: [CodexRolloutParser.swift](../../../Shared/Analytics/CodexRolloutParser.swift)).

**Ключевое:** окно берём из `windowDurationMins`, а не из имени поля. У Орки
здесь баг — она жёстко считает `primary` пятичасовым окном, и в её кэше лежит
`"5h": {"pct": 34, "window_minutes": 10080}`. На Pro сейчас у `primary` окно
10080 минут (неделя), а `secondary` пустой. Раскладка по позиции сломается при
первом же изменении на стороне OpenAI.

### 3.2 Claude — OAuth-эндпоинт

Токен: запись Keychain `Claude Code-credentials`, аккаунт — имя пользователя,
внутри JSON, поле `claudeAiOauth.accessToken`. Дальше:

```
GET https://api.anthropic.com/api/oauth/usage
Authorization: Bearer <token>
anthropic-beta: oauth-2025-04-20
User-Agent: claude-code/2.1.0
```

Ответ: `{"five_hour": {"utilization": 75, "resets_at": "…ISO…"},
"seven_day": {…}}`. Окна — 5 часов и неделя.

**Эндпоинт жёстко троттлится.** Второй запрос подряд вернул
`429 rate_limit_error` с `Retry-After: 3582` — почти ровно час. Опрашивать
по таймеру виджета нельзя. Раз в час, с уважением к `Retry-After`, и подпись
«данные на HH:MM» в интерфейсе обязательна.

Эндпоинт недокументированный, найден строками в бинаре CLI 2.1.181 рядом с
заголовками `anthropic-ratelimit-unified-*`. Может отвалиться при обновлении
Claude Code — считаем это штатным риском и деградируем в плашку, а не в ноль.

Скрейп TUI через `pty.fork` (как в [claude_tui_usage.py](/Users/sergeytovarov/orca/app/core/claude_tui_usage.py))
не портируем: поднимать псевдотерминал с полноценным Claude Code из меню-бар
приложения ради двух чисел — плохой размен.

### 3.3 OpenCode Go — cookie + скрейп

API-ключи из `~/.local/share/opencode/auth.json` не подходят: они дают доступ
к моделям, а не к квоте подписки. Нужна сессионная cookie сайта
(`auth=Fe26.2**…`), которую пользователь достаёт руками из DevTools
opencode.ai. Дальше: `GET /_server?id=…` → id воркспейса (`wrk_…`) →
`GET /workspace/<id>/go` → HTML в формате React Flight → регуляркой достаём
`rollingUsage` / `weeklyUsage` / `monthlyUsage`, у каждого `usagePercent` и
`resetInSec`. Окна: 5 часов, неделя, месяц.

Cloudflare режет дефолтный UA — ходим с браузерным. Проверено живьём: cookie
из `~/orca/.env` рабочая, воркспейс определился сам, все три окна вернулись.

Самое хрупкое звено: cookie протухает, автообновления нет, вёрстка страницы
может поменяться в любой день. Деградация — обязательна.

## 4. Модель данных

Окна не хардкодим по позиции. Провайдер отдаёт набор окон, каждое описывает
себя длительностью.

```swift
enum LimitProvider: String, Codable { case claude, codex, opencode }

struct LimitWindow: Codable, Equatable {
    let windowMinutes: Int      // 300 | 10080 | 43200
    let usedPercent: Double     // 0…100
    let resetsAt: Date?
}

enum LimitStatus: String, Codable {
    case ok            // цифры свежие
    case stale         // последний опрос не удался, показываем прошлые
    case throttled     // 429, ждём Retry-After
    case unauthorized  // токен/cookie протухли — нужно действие пользователя
    case unconfigured  // cookie не введена
    case unavailable   // источника нет (не установлен codex)
}

struct ProviderLimits: Codable {
    let provider: LimitProvider
    let windows: [LimitWindow]
    let status: LimitStatus
    let fetchedAt: Date?
    let error: String?
}
```

Значение кольца провайдера = `usedPercent` того окна, у которого **самый
ранний `resetsAt`**. Это прямой ответ на вопрос «сколько осталось в ближайшее
время»: у Claude это пятичасовое окно, у Codex — недельное (другого нет), у
OpenCode — пятичасовое. Окна без `resetsAt` в выборе не участвуют; если
времени сброса нет ни у одного окна — берём самое короткое по длительности.

Известное следствие: короткое окно сбрасывается часто и потому почти всегда
близко к нулю. Расклад «5ч на 0%, неделя на 95%» нарисует спокойное почти
пустое кольцо ровно перед тем, как человек упрётся. Раньше это компенсировалось
цветом — кольцо краснело от худшего окна, — но от порогов отказались (см. §7.1),
и сигнала тревоги в меню-баре больше нет. Размен принят сознательно: полоски
всех окон в попапе показывают полную картину, а различимость трёх колец между
собой оказалась важнее.

## 5. Хранилище

Миграция GRDB v10, две таблицы. Существующую `analytics_rate_limits` не
трогаем — у неё другая задача (историческая аналитика за 30 дней), и она
живёт от ингестора транскриптов.

```sql
CREATE TABLE limit_snapshots (
    id             INTEGER PRIMARY KEY AUTOINCREMENT,
    provider       TEXT NOT NULL,
    window_minutes INTEGER NOT NULL,
    used_percent   REAL NOT NULL,
    resets_at      INTEGER,
    observed_at    INTEGER NOT NULL
);
CREATE INDEX idx_limit_snapshots_lookup
    ON limit_snapshots(provider, window_minutes, observed_at DESC);

CREATE TABLE limit_fetch_state (
    provider        TEXT PRIMARY KEY,
    last_attempt_at INTEGER,
    last_success_at INTEGER,
    status          TEXT NOT NULL,
    error           TEXT,
    retry_after_at  INTEGER
);
```

Снапшот пишем, только если пара `(used_percent, resets_at)` отличается от
последней записи по этому `(provider, window_minutes)`. Получается ступенчатая
кривая без мусора — ровно то, что нужно второму этапу для темпа расхода.
Ретеншен: чистим записи старше 60 дней при каждом успешном опросе.

## 6. Расписание опроса

| Провайдер | Период | Почему так |
|---|---|---|
| Codex | 5 мин | Локально, дёшево, спавн процесса ~1с |
| OpenCode | 15 мин | Сеть + Cloudflare, чаще незачем |
| Claude | 60 мин | Жёсткий троттлинг эндпоинта, `Retry-After` ~3582с |

Опрос вешаем на существующий `SyncCoordinator` — там уже живёт часовой хук
ингеста аналитики.

**Оговорка про фактический пол расписания.** Тик лимитов едет на общем таймере
синхронизации, а он по умолчанию раз в 15 минут. Значит периоды из таблицы —
это потолок частоты, а не гарантия: реально Codex будет опрашиваться не чаще,
чем идёт синк. Отдельный таймер под лимиты заводить не стали — лимиты
сбрасываются через часы и дни, разница между пятью минутами и пятнадцатью на
поведение фичи не влияет, а второй жизненный цикл пришлось бы гасить при
выходе и будить после сна. На 429 ставим `retry_after_at` и до этого времени провайдер
не трогаем вообще. На старте приложения — один опрос всех трёх, если последний
успех старше периода.

WidgetKit-виджет на рабочем столе в v1 лимиты не показывает — поверхности две,
капсула и попап, обе живут в процессе приложения. Значит `WidgetSnapshot`
трогать не нужно и схему снапшота не ломаем. Если лимиты понадобятся на
десктопном виджете, поля добавятся аддитивно через `decodeIfPresent`, как
делались поля советника.

## 7. Интерфейс

### 7.1 Капсула меню-бара

Три отдельных кольца в ряд справа от цены, по кольцу на провайдера, каждое
своего цвета. Размер около 10pt, суммарно ~40pt ширины.

```
┌────────────────────────────────┐
│  ◉  $1,602.78    ◔  ◕  ○      │
└────────────────────────────────┘
                  cl cx  oc
```

Заполнение — по ближайшему к сбросу окну (см. §4). Цвет — **фирменный цвет
провайдера, всегда один и тот же**. Провайдер не в статусе `ok` — кольцо серое,
пунктиром.

Пороги 70% и 90%, на которых цвет уходил в жёлтый и красный, убраны после
первого же взгляда на живой интерфейс: три кольца идут подряд без подписей, и
цвет — единственное, чем они отличаются. Когда Codex покраснел на 96%, ряд
превратился в три одинаковых пятна. Цвет здесь опознавательный знак, а не
сигнал тревоги; насколько всё плохо, показывает заполненность.

Фирменные цвета:

| Провайдер | Цвет | Значение |
|---|---|---|
| Codex | синий | `#3B82F6` — намеренно отличается от существующего `BrandColor.cyan` (`#00B8E6`), иначе сольётся с акцентом приложения |
| Claude | рыжий | `#D97757` — фирменный оранжевый Anthropic; на тёмной капсуле осветляем до `#E8875F` |
| OpenCode | белый | `#FFFFFF` |

**Белое кольцо требует отдельной обработки.** Меню-бар в светлой теме светлый,
и белый штрих в 1.5–2pt на нём исчезает — у текста капсулы та же заливка, но
глиф толще и потому читается. Поэтому: трек (незаполненная часть) у всех колец
не «свой цвет с прозрачностью», а нейтральный `Color.primary.opacity(0.15)`,
плюс у кольца тонкий контур `Color.black.opacity(0.25)` шириной 0.5pt. На
тёмном фоне контур не виден, на светлом — держит форму. Проверяется глазами в
обеих темах, автотестом такое не ловится.

Цвет и заполнение намеренно берутся из разных окон. Заполнение отвечает на
«сколько я могу сделать прямо сейчас», цвет — на «не пора ли тормозить
вообще». Одно окно на оба вопроса не отвечает.

### 7.2 Вкладка «Расходы»

Под текущим блоком с ценой и топом моделей — секция «Лимиты»: три строки, в
каждой название провайдера, полоски по окнам с процентом, время до сброса
человеческим текстом («сброс через 14ч»), и подпись «данные на 14:22».

Для `unauthorized` и `unconfigured` вместо полосок — строка действия: «Claude:
нужен вход заново» / «OpenCode: вставь cookie в настройках».

### 7.3 Настройки

Новая секция в общей вкладке: поле для cookie OpenCode (`SecureField`),
кнопка «Проверить» с немедленным опросом и показом результата, и короткая
инструкция, откуда cookie взять.

## 8. Секреты

Cookie OpenCode — секрет. Хранится **только** в Keychain через существующий
[KeychainStore](../../../StatsApp/Network/KeychainStore.swift), сервис
`ai-stats.opencode`, аккаунт — имя пользователя. Ни в `UserDefaults`, ни в
файлах, ни тем более в репозитории. В логи не пишем ни при каких условиях, в
том числе в текст ошибки.

Токен Claude читаем из чужой записи Keychain и **никуда не сохраняем** — взяли,
сходили, забыли. Приложение не в сэндбоксе, доступ разрешён, но macOS покажет
диалог подтверждения. При ad-hoc подписи (`CODE_SIGN_IDENTITY: "-"`) диалог
будет вылезать после каждой пересборки — в дев-цикле это надо просто пережить.

## 9. Деградация

Ни одно состояние не показывает выдуманных чисел.

- Опрос не удался, есть прошлые данные — рисуем их, статус `stale`, подпись
  «данные на HH:MM» становится приглушённой.
- Прошлых данных нет — кольцо серое пунктиром, в попапе «нет данных».
- 429 — статус `throttled`, показываем прошлые цифры и время следующей попытки.
- Токен/cookie протухли — статус `unauthorized`, строка действия. Молча
  показывать старые проценты нельзя: человек примет решение по вранью.

## 10. Тесты

Парсеры — чистые функции, тестируются на фикстурах без сети и процессов:
разбор ответа `/api/oauth/usage`, разбор JSON-RPC ответа Codex (включая случай
`secondary: null` и окно 10080 в `primary`), разбор React Flight страницы
OpenCode (включая `monthlyUsage: null`).

Отдельно: дедупликация снапшотов, ретеншен 60 дней, поведение на 429 с
`Retry-After`, постоянство цветов провайдеров и выбор окна для кольца —
включая случай «ни у одного окна нет `resetsAt`».

Сетевые вызовы — через протокол с фейком в тестах, как сделано у существующих
фетчеров.

## 11. Риски

| Риск | Что делаем |
|---|---|
| `/api/oauth/usage` недокументирован, может исчезнуть | Статус `unavailable` + плашка, не падаем |
| Cookie OpenCode протухает молча | Статус `unauthorized`, явная строка действия |
| Вёрстка страницы OpenCode поменяется | Парсер возвращает nil → `stale`, тест на фикстуре поймает при обновлении |
| Троттлинг Claude строже часа | Уважаем `Retry-After`, никогда не ретраим агрессивно |
| Диалог Keychain при каждой пересборке | Известное неудобство дев-цикла, в релизной сборке одноразовое |
| Кольца ломают вёрстку узкой капсулы | Кольца скрываются, если все три провайдера без данных |

## 12. Объём

Грубо: слой источников (три фетчера + протокол) — самый большой кусок,
хранилище с миграцией и дедупом — средний, интерфейс (кольца, секция в
попапе, настройки) — средний, тесты — сопоставимо с источниками.

Порядок работ: миграция и модель → фетчер Codex (самый простой и проверяемый)
→ фетчер Claude → фетчер OpenCode → расписание в `SyncCoordinator` →
секция в попапе → кольца в капсуле → настройки с cookie.

Первые три шага дают работающую фичу на одном Codex — дальше наращивается
без переделок.

## 13. Открытые вопросы

- Сигнала «ты почти упёрся» в меню-баре теперь нет вовсе: цвет постоянный, а
  заполненность считается по ближайшему окну. Если это начнёт мешать — думать
  надо не про цвет, а про какой-то отдельный признак, не ломающий различимость
  колец.
- Читаемость белого кольца в светлой теме проверяется только глазами. Если
  контура 0.5pt не хватит — придётся либо утолщать штрих, либо отходить от
  чистого белого к очень светлому серому.

## 14. Хвосты после реализации

Ветка `feat/limits-monitor` смержена с известными недоделками. Решение владельца
по итогам финального ревью: чиним только критичное, остальное живёт здесь.
Критичных на момент мёрджа не осталось.

### Требует человека, не автоматизируется

- **Кольца в светлой и тёмной теме не проверены глазами.** Приложение
  menu-bar-овое (`LSUIElement`), скриншотить его нечем — ни один агент этого не
  сделал и сделать не может. Смотреть надо: читается ли белое кольцо OpenCode на
  светлом меню-баре, не обрезана ли капсула справа, различимы ли три кольца при
  диаметре 10pt. Если контура 0.5pt не хватает — либо толще штрих, либо уйти от
  чистого белого к очень светлому серому, и записать выбор в §13.

### Известные дефекты

- **Подпись «нет данных» поверх реальных цифр у фолбэка Codex.**
  `LimitsRepository.record()` не сохраняет `limits.fetchedAt`, а `latest()`
  собирает подпись из `lastSuccessAt`, который двигается только при статусе
  `ok`. У кого RPC codex не работает — а фолбэк ровно для них — попап покажет
  настоящие проценты с подписью «нет данных» вместо «данные на HH:MM,
  несвежие». Противоречит §9. Заодно делает мёртвым кодом чтение времени
  модификации rollout-лога. Чинится персистом `fetchedAt` — фетчеры его уже
  считают честно.
- **`restored = true` ставится даже при неудачном чтении базы**
  (`LimitsCoordinator`). Разовый сбой на старте теряет окно троттлинга на всю
  жизнь процесса — ровно то, ради чего восстановление и делалось. Флаг надо
  ставить только при успехе.
- **Форс-тик лимитов на старте ждётся синхронно.** Один Codex закладывает до 12
  секунд таймаута плюс два сетевых запроса; всё это время попап и капсула держат
  пустоту. Развязывается отдельной задачей.
- **Каждый клик «Проверить» в настройках создаёт `URLSession` без
  `invalidateAndCancel`** — сессия держит себя сама до инвалидации, то есть
  течёт. Три долгоживущих фетчера этим не страдают, они создаются один раз.
- **Ручная проверка cookie не видна работающему координатору.** `recordManualCheck`
  пишет в базу, но in-memory расписание актора не обновляется: проверка,
  вернувшая `throttled`, не остановит следующий опрос. Самолечится рестартом.
- **`__Host-auth=` в `normalizeCookie` сравнивается регистрозависимо**, хотя
  соседняя `auth=` — нет. Ввод `__Host-Auth=…` завернётся в мусор вида
  `auth=__Host-Auth=…`. Родня уже починенной находки про `Auth=`.
- **`Auth=` с большой буквы теперь долетает до сервера и отвергается им**
  вместо того, чтобы исчезать молча. Тихая потеря устранена, но имена cookie в
  HTTP регистрозависимы — до конца юзкейс не закрыт.

### Осознанно оставлено

- **Busy-wait в `CodexLimitsFetcher` починен** после финального ревью, несмотря
  на более раннее решение оставить: цена оказалась выше заявленной — не только
  сожжённое ядро, но и занятый поток кооперативного пула на 12 секунд.
- **Нет инжекции `locateCodex`**, поэтому два теста фетчера Codex ветвятся по
  окружению машины. На машине с системным codex `test_falls_back_to_newest_rollout_snapshot`
  проверяет не фолбэк, а живой спавн. Чинится одной строкой DI, если начнёт мешать.
- **Прунинг снапшотов идёт на каждом тике**, а не после успешного опроса, и не
  покрыт индексом. Таблица маленькая, вреда нет.
- **`KeychainStore` и `LimitsRepository` не `Sendable`.** Взорвётся при переезде
  на строгий concurrency Swift 6 — чинить одним заходом по всему проекту.
- **`DropdownLimitsSection` без тестов**: логика выбора ветки отрисовки
  (действие / полоски / нет данных) держится только на ревью.
